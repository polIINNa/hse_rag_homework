# Описание реализации RAG

## Архитектура

Реализация находится в [`eval/rag_example.py`](eval/rag_example.py), класс `RAG`.

### 1. Извлечение текста из PDF
- Источник метаданных: `data/documents.jsonl` (`doc_id`, `path`, организация, число страниц).
- PDF открываются из `data/reports/<path>` с помощью **PyMuPDF (`fitz`)**.
- Текст извлекается **постранично**: для каждой страницы сохраняются `doc_id`, номер страницы `page` (1-based, как в разметке), путь, организация и текст.
- Текст нормализуется (схлопывание пробелов), пустые страницы не индексируются.

**Зачем:** метрики контекста считаются по парам `(doc_id, page)`, поэтому важно сохранять точные идентификаторы и номера страниц.

### 2. Чанкинг и индекс с эмбеддингами
- Каждая страница дополнительно разбивается на **перекрывающиеся чанки** (~1200 символов, overlap ~200). 
- Для каждого чанка считается эмбеддинг локальной моделью **`sentence-transformers`** (по умолчанию `intfloat/multilingual-e5-small`, `EMB_MODEL`).
- Для e5 используются префиксы `passage:` (чанки) и `query:` (запрос). Эмбеддинги нормализуются, сходство — косинусное.
- Кэш v2: `eval/cache/chunks_v2.jsonl` и `eval/cache/embeddings_v2.npy`.

**Зачем:** чанки точнее соответствуют локальным таблицам/фрагментам, чем целая страница, что повышает шанс найти нужную страницу.

### 3. Поиск (retrieval) с метаданным бустом
- Из вопроса эвристически извлекаются подсказки: банк/организация (по ключевым словам → префикс `doc_id`), год, период (`6m`/`annual`).
- К базовому косинусному скору добавляется мягкий **буст/штраф** по совпадению `doc_id` (org/year/period).
- Отбираются top кандидаты-чанки, затем агрегируются до **лучшего скора на страницу** и выбираются top-N страниц (`RAG_TOP_K`, по умолчанию **8**).
- Результат группируется по `doc_id` в формате:
  ```json
  [{"doc_id": "...", "pages": [1, 2]}]
  ```

**Зачем:** в финансовых вопросах почти всегда указан банк и период; буст по метаданным повышает recall/precision поиска нужного отчёта.

### 4. Генерация ответа
- Для найденных страниц в промпт передаётся **полный текст страницы** (все её чанки, а не только лучший чанк) с указанием `doc_id`, страницы и скора.
- Если задан `GEN_API_KEY` или `LLM_API_KEY`, выполняется запрос к LLM API (по умолчанию `https://claude.gigaparsers.ru/v1/messages`, `GEN_MODEL`=`deepseek-flash`) с инструкцией отвечать **только по контексту**, точно сохранять числа/валюты/единицы/периоды и отвечать на все части составного вопроса. В запросе отключён reasoning (`thinking: disabled`), чтобы `max_tokens` не расходовался на размышления и ответ не приходил пустым.
- При пустом ответе LLM — повторная попытка, затем извлекающий fallback; при отсутствии ключа/ошибке API — сразу fallback (для проверки retrieval).

> Примечание: текущая реализация использует локальные эмбеддинги (`sentence-transformers`), внешний `EMB_KEY` не требуется.

### 5. Воспроизводимость времени ответа
- Модель эмбеддингов загружается и один раз прогревается в `RAG.__init__` (до начала цикла оценки). Иначе загрузка модели попадала бы в `time` первого вопроса и заметно искажала среднее.
- Генерация выполняется с `temperature=0` и отключённым reasoning, поэтому ответы и время стабильнее между запусками.

## Используемые библиотеки
- `pymupdf` — извлечение текста из PDF
- `sentence-transformers`, `torch`, `numpy` — эмбеддинги и векторный поиск
- `requests` — HTTP-запросы к LLM API
- `openpyxl` — формирование Excel-отчёта (eval)

## Параметры (переменные окружения)
| Переменная | Назначение | По умолчанию |
| --- | --- | --- |
| `LLM_API_KEY` | Ключ для LLM-судьи (`eval/eval_functions.py`, оценка `answer_correctness`). Также может использоваться для генерации, если `GEN_API_KEY` не задан. | — |
| `GEN_API_KEY` | Ключ для генерации ответа в RAG (предпочтительно, если отдельный от судьи). | = `LLM_API_KEY` |
| `GEN_BASE_URL` | Endpoint генерации (Anthropic Messages-совместимый формат, как в проекте). | `https://claude.gigaparsers.ru/v1/messages` |
| `GEN_MODEL` | Модель генерации. | `deepseek-flash` |
| `EMB_MODEL` | Локальная модель sentence-transformers для эмбеддингов. | `intfloat/multilingual-e5-small` |
| `RAG_TOP_K` | Количество извлекаемых страниц. | `8` |

> Примечание: в базовой реализации эмбеддинги считаются **локально** (sentence-transformers), поэтому отдельный API-ключ эмбеддера не требуется. Если у вас есть ключ сервиса эмбеддингов (`EMB_KEY` в условии) — это относится к варианту использования внешнего сервиса эмбеддингов; текущий код его не использует.

## Известные ограничения
- Три PDF — сканы без текстового слоя: `alfa_2024_annual` (`alfa/2024/annual.pdf`), `gpb_2023_annual` (`gpb/2023/annual.pdf`), `gpb_2025_annual` (`gpb/2025/annual.pdf`). PyMuPDF возвращает для них пустой текст, поэтому страницы не попадают в индекс. В `data/test.jsonl` 18 вопросов, где эти документы указаны в `gold_context`; для них `context_recall` = 0. Для улучшения нужен OCR (например, Tesseract/PaddleOCR) и переиндексация.
- Сложные таблицы индексируются как текст (без восстановления структуры строк/колонок); это может снижать точность на вопросах, где число нужно найти в ячейке большой таблицы.
